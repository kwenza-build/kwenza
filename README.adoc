= kwenza
:toc:
:toclevels: 2

_"kwenza" — isiXhosa for "to make."_

A simple, declarative build tool for the JVM. Where Maven and Gradle carry decades of
flexibility (XML lifecycles, a Groovy/Kotlin scripting DSL, plugin ecosystems), kwenza aims to
stay small and inert: your `kwenza.toml` is data, not a program, and the tool has exactly one way
to do each thing.

It's still fully interoperable with the existing Java ecosystem: real transitive dependency
resolution against Maven Central, a local cache that's byte-for-byte your existing
`~/.m2/repository`, and the standard `src/main/java` directory layout. Existing Java tooling,
IDEs, and caches keep working.

The name is deliberately not Java-specific — the door's left open for kwenza to grow support for
other JVM languages (Kotlin, say) later without an awkward rename.

== Status

*Working now:* dependency resolution, compilation, packaging, running, and a lockfile — the full
inner loop for a single-module Java project.

*Not built yet* (tracked as a deliberate Phase 2, not oversights): running tests (JUnit), a
`--fat` uber-jar option, multi-module workspaces, a `[scripts]` task runner, and an `--offline`
mode. See link:AGENTS.md[AGENTS.md] for the reasoning behind what's in and out of scope so far.

== Quick start

kwenza builds itself, so the very first jar has to come from a plain `javac`/`jar` bootstrap
script:

[source,bash]
----
git clone <this-repo> && cd kwenza
./bootstrap.sh              # produces .bootstrap/kwenza-bootstrap.jar (outside target/, survives `kwenza clean`)
bin/kwenza package          # from here on, kwenza rebuilds itself using itself
----

Put `bin/` on your `PATH` so `kwenza` is just a command, then, in any project directory
containing a `kwenza.toml`:

[source,bash]
----
kwenza build      # resolve dependencies + compile
kwenza test       # build + compile src/test/java + run it via the JUnit Platform Console Launcher
kwenza run        # build + execute [package].main-class
kwenza package    # build + produce a runnable thin jar
----

See link:docs/modules/ROOT/pages/getting-started.adoc[Getting Started] for the full walkthrough,
including a from-scratch new project.

== Benchmarks

link:benchmarks[`benchmarks/`] times kwenza against Maven and Gradle across a growing set of real
scenarios (a trivial app, a small library with real JUnit 5/Mockito tests, more over time), using
fully isolated dependency caches so it's safe to re-run anytime (`java benchmarks/Bench.java`, no
build step). Latest hello-world results: kwenza resolves cold roughly 12x faster than Maven/Gradle,
and beats Maven warm too — though Gradle's persistent daemon edges out kwenza once it's warm, a
known trade-off of kwenza launching a fresh JVM per invocation rather than keeping one running.
See link:benchmarks/README.adoc[`benchmarks/README.adoc`] for how to run it, and
link:benchmarks/hello-world/README.adoc[that scenario's own README] for the full numbers,
methodology, and how to read them honestly.

== Contributing

Commit messages follow https://www.conventionalcommits.org/[Conventional Commits]
(`feat: ...`, `fix(resolver): ...`, `feat(cli)!: ...` for breaking changes). This isn't enforced by
tooling — a hook would only run for contributors who'd manually activated it (git never tracks
`.git/config`, so there's no way to ship that automatically without either relying on Node/Python
tooling or having `bootstrap.sh` reach beyond its actual job of bootstrapping the build), which
makes unenforced-but-inconsistent worse than just stating the convention. Follow it by hand.
