= CLI Reference
:toc:
:toclevels: 2

Every kwenza command runs against the current working directory — there's no `--project <path>`
flag (yet); `cd` into the project you want to build, same as Maven, Gradle, or Cargo.

Multiple commands can be given in one invocation and run in the order given, e.g.
`kwenza clean build run` or `kwenza build run`. Resolving and compiling only happen once per
invocation no matter how many chained commands would each otherwise trigger them — `kwenza build
run` resolves and compiles a single time, then `run` reuses that result instead of redoing it.
`clean` correctly invalidates that: `kwenza build clean package` recompiles after the `clean`,
it doesn't reuse the now-deleted output from the `build` earlier in the same chain. An unknown
command anywhere in the list is rejected upfront, before any of the given commands run.

== Commands

=== `kwenza build`

Resolves dependencies (from the lock if it's fresh, from Maven Central otherwise) and compiles
`src/main/java` to `<output-dir>/classes`. Copies `src/main/resources` verbatim alongside the
compiled classes, if that directory exists. Produces no packaged artifact.

=== `kwenza run`

Runs `build`, then executes `[package].main-class` in a fresh `java` subprocess, with the
compiled classes and every resolved dependency jar on the classpath. Fails with a clear error if
`main-class` isn't set in `kwenza.toml`. The subprocess inherits stdin/stdout/stderr, and kwenza
exits with the same exit code the subprocess used.

kwenza prints the command it's about to run as a `run: ...` status line before launching it, so
there's no hidden invocation to guess at — there's no packaged jar involved, just the compiled
classes directory and dependency jars directly on the classpath. By default this is a compact
one-liner (relative classes path, dependency jars summarized as a count):

[source]
----
run: java -cp target/classes (+7 dependency jars) com.example.Main
----

Pass `--verbose` to *also* print the literal command actually executed — full `java` binary path
and every classpath entry — as an indented detail line underneath:

[source]
----
run: java -cp target/classes (+7 dependency jars) com.example.Main
  /path/to/jdk/bin/java -cp target/classes:/home/you/.m2/repository/.../guava-33.2.1-jre.jar:... com.example.Main
----

NOTE: kwenza's own status messages (`resolve: ...`, `compile: ...`) print to *stderr*, not
stdout — so `kwenza run`'s stdout is exactly what your program itself printed, nothing else.
`kwenza run > out.txt` captures only your application's real output. See <<output>> below for how
kwenza's own messages are formatted and colored.

=== `kwenza package`

Runs `build`, then writes `<output-dir>/<name>-<version>.jar` — a thin jar containing only your
project's own classes/resources, with a `Class-Path` manifest entry pointing at the cached
dependency jars (see link:architecture.adoc[Architecture]). Runnable directly:

[source,bash]
----
kwenza package
java -jar target/my-app-0.1.0.jar
----

=== `kwenza clean`

Deletes the entire output directory (`target/` by default, or whatever `[package] output-dir` is
set to). Reports `clean: nothing to remove` rather than erroring if it doesn't exist.

=== `kwenza resolve`

Refreshes `kwenza.lock` explicitly, without compiling or packaging anything. Mostly useful with
`--update`, to intentionally pull newer dependency versions on your own schedule rather than as a
side effect of some other command.

[[output]]
== Output

kwenza's own status messages always print to stderr, one per task, prefixed with the task's
name (`resolve: ...`, `compile: ...`, `package: ...`, `clean: ...`) — including when
a command implicitly chains several tasks, e.g. `kwenza run` resolving and compiling before it
executes anything. This keeps a multi-task command's progress legible at a glance, and keeps
`kwenza run`'s stdout as pure application output (see the `run` note above).

When stdout is an actual terminal, these messages print in cyan (errors in red) so they're
visually distinct from whatever your application itself prints. Color is automatically suppressed
when output isn't a real terminal (piped, redirected to a file) or when the
https://no-color.org/[`NO_COLOR`] environment variable is set to any value.

With `--verbose`, a real dependency resolution (a stale/missing lock, or `--update`) also prints
one dimmed detail line per resolved artifact, in a third color (gray) distinct from both the
regular cyan status lines and a running application's own output. Detail lines are indented but
not re-labeled with a task name — the cyan line immediately above already establishes the
context:

[source]
----
resolve: fetching dependencies from Maven Central...
  com.google.guava:guava:33.2.1-jre  (direct)
  com.google.guava:failureaccess:1.0.2  (via com.google.guava:guava)
  com.google.guava:listenablefuture:9999.0-empty-to-avoid-conflict-with-guava  (via com.google.guava:guava)
resolve: 7 artifact(s) resolved -> kwenza.lock
----

This only appears when dependencies are actually being fetched over the network — resolving from
an already-fresh `kwenza.lock` has nothing per-artifact to show, so `--verbose` doesn't print
anything extra in that case. `run --verbose` follows the same pattern: the usual cyan summary
line, then the full command as an unlabeled gray detail line underneath (see `kwenza run` above).

== Flags

[cols="1,3"]
|===
|Flag |Effect

|`--update`
|Forces a full re-resolution against Maven Central, ignoring `kwenza.lock` even if it looks fresh.
Valid alongside `build`, `run`, `package`, and `resolve`.

|`--verbose`
|Prints extra detail, see <<output>>: one line per resolved dependency during a real resolution
(any command that resolves), and, for `run` specifically, the literal command being executed
(full `java` binary path, every classpath entry) instead of the default compact one-liner.
|===

== Environment variables

[cols="1,3"]
|===
|Variable |Effect

|`KWENZA_REPO`
|Overrides the local dependency cache directory (default: `~/.m2/repository`). Used internally by
link:../benchmarks/hello-world/run.sh[`benchmarks/hello-world/run.sh`] to keep benchmark runs
fully isolated from your real Maven cache, but it's a generally useful override on its own — e.g.
for CI, or keeping multiple unrelated cache states around.

|`KWENZA_TIMING`
|Set to any value to print a phase-timing breakdown to stderr: JVM bootstrap time, then the
elapsed time between each of manifest-load / resolve / compile / package. Distinguishes JVM
startup overhead (invisible to a shell-level wall-clock timer) from time spent in kwenza's own
logic — see link:architecture.adoc[Architecture] for how this was used to diagnose kwenza's
own cold-start cost.
|===

Example `KWENZA_TIMING` output:

[source]
----
resolve: using locked dependencies (kwenza.lock)
compile: target/classes
package: target/hello-world-0.1.0.jar
[timing] jvm-bootstrap-to-main: 20ms
[timing] main-entry -> manifest-loaded: 3ms
[timing] manifest-loaded -> resolved (from lock): 111ms
[timing] resolved (from lock) -> compiled: 275ms
[timing] compiled -> packaged: 4ms
[timing] main-entry -> packaged (total): 395ms
----
