== Daemon and no-daemon

kwenza starts a fresh JVM for every command and keeps nothing running between them. Maven does
the same. Gradle's default is the opposite: the first build starts a background daemon, and every
later build reuses it, with its classes already loaded and its compiler already optimised by the
JIT. That is a real advantage on a repeated build, and it is why Gradle's warm figures are
much lower than its no-daemon ones.

So the charts show Gradle twice:

Gradle (daemon)::
`./gradlew` as most people run it. The timed builds reuse a daemon that earlier builds in the
same run already started and warmed. This is the figure to compare against if you build over and
over in one session.

Gradle (no daemon)::
`./gradlew --no-daemon`. Every build pays for a fresh JVM, as kwenza and Maven do. This is the
like-for-like comparison of the build logic itself, and the one that matches a CI job, where a
build normally starts on a machine with no daemon.

Neither is the "right" one. They answer different questions, and a fair reading uses both.

kwenza may gain an optional daemon later, for the same reason: a warm process is the only way to
remove JVM start-up and class loading from every build, and that cost matters most on small
projects and in a tight edit-and-rebuild loop. It isn't built, so none of the figures here
include one. If it arrives, it will be opt-in and these pages will show it as its own line. See
xref:design-principles.adoc[] for why kwenza doesn't have one today.

== What was measured

Four tools and four scenarios. Every tool builds the *same source*: each tool's `src` is a
symlink to one copy, and only the manifest (`kwenza.toml`, `pom.xml`, `build.gradle.kts`)
differs.

[cols="2,3,2"]
|===
|Scenario |Project |Operations

|`hello-world`
|https://github.com/kwenza-build/kwenza/tree/main/examples/hello-world[`examples/hello-world`]: one
source file, one dependency (Guava). Mostly measures the fixed cost of starting the tool.
|`package`

|`junit-word-count`
|https://github.com/kwenza-build/kwenza/tree/main/examples/junit-word-count[`examples/junit-word-count`]:
a small library with one dependency (Guava) and a real JUnit 5 test and Mockito test.
|`package`, `test`

|`commons-lang3`
|https://github.com/apache/commons-lang[Apache Commons Lang 3.19.0]: 259 source files, about
100,000 lines, no dependencies. Mostly measures `javac` on a real code base.
|`package`
|===

=== What each operation does

`package`:: Compile the main sources and build the jar. *Tests are not compiled or run*, for any
tool. Maven's `package` and Gradle's `build` run the tests by default, so the harness uses
Maven's `package` with `-Dmaven.test.skip=true` and Gradle's `assemble`, which doesn't depend on
`test`. Otherwise "package" would include running tests for those two and not for kwenza.

`test`:: Resolve dependencies, compile the main sources, compile the test sources and *run the
tests*, then report. For `junit-word-count` that is the JUnit 5 and Mockito tests. Each tool does
this in its own way: kwenza starts a separate JVM running the JUnit console launcher, Maven runs
Surefire, and Gradle runs a test worker. Only `junit-word-count` has tests in the benchmark;
`commons-lang3`'s tests are not run.

Both operations are a *clean* build: the output directory (`target` or `build`) is deleted before
every timed run, so every run compiles from source. Maven's and Gradle's own incremental or build
caches are not used.

=== Warm and cold

Warm::
The dependency caches are already populated, so no run touches the network. The harness does one
untimed run first, then times the stated number of clean rebuilds and reports the median and the
fastest. kwenza builds from its `kwenza.lock`; Maven and Gradle use their local caches. Gradle's
daemon, when it is used, is started by the untimed run and stopped after the last timed one.

Cold::
The tool's dependency cache is deleted first (and `kwenza.lock` for kwenza), so the run resolves
and downloads everything from Maven Central, and each tool does one timed run. This measures the
network as much as the tool, so treat it as indicative. The downloaded Maven and Gradle
_wrapper distributions_ are left in place, since fetching a ~120 MB build tool isn't part of
building your project.

Every tool uses its own isolated cache directory, never your real `~/.m2` or `~/.gradle`: kwenza
through `KWENZA_REPO`, Maven through `-Dmaven.repo.local` and Gradle through `GRADLE_USER_HOME`. The
timing is the wall-clock time of the whole process, from launch to exit, so it includes JVM
start-up for every tool that isn't running as a daemon.

Each tool is started through its launcher script: `bin/kwenza`, `./mvnw` and `./gradlew`. kwenza's is
a few lines of shell that find the jar and run `java -jar` on it, which adds about 25 ms to a
build.

== Reading the results

* The charts and tables are one machine, one day. Differences of a few percent are noise;
  the harness reports the fastest run next to the median to help you see how noisy a row was.
* Where the time goes changes with project size. A small project is mostly start-up cost, which
  a fresh JVM per build pays in full and a warm daemon doesn't. A large one is mostly `javac`,
  where a daemon's already-optimised compiler is the advantage. So the order of the tools can
  differ between scenarios; look at each row rather than expecting one tool to win everywhere.
* Not measured: Maven's own daemon, https://github.com/apache/maven-mvnd[mvnd]; builds that reuse
  earlier output (incremental builds); and test suites other than `junit-word-count`'s.
* kwenza's own start-up isn't tuned yet. Class Data Sharing and a daemon are both ideas
  that haven't been adopted, so these figures are a starting point, not a ceiling.

== Repeat it

You need a JDK, and the first run downloads the Maven and Gradle wrappers. From a checkout of
https://github.com/kwenza-build/kwenza[kwenza]:

[source,bash]
----
bin/kwenza package                              # the kwenza jar the harness times
cd benchmarks
java Bench.java                                 # every scenario, cold and warm
java Bench.java commons-lang3 warm 10           # one scenario, warm only, 10 runs
java Bench.java all both 7 --write-docs         # also regenerate this page's tables and charts
----

The harness, the three project definitions for each scenario and a README on how it works are in
https://github.com/kwenza-build/kwenza/tree/main/benchmarks[`benchmarks/`]. If you get different
results on your machine, or think a tool is being run unfairly, please open an issue.
