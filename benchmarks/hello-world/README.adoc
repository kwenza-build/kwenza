= hello-world benchmark
:toc:
:toclevels: 2

Times kwenza against Maven and Gradle building the exact same trivial app — same
`com.example.Main`, same single Maven Central dependency (Guava), same Java 21 target. One
scenario among what `benchmarks/` is meant to hold over time; this is the first and simplest
(single file, one dependency), not the only one planned.

== Layout

[source]
----
hello-world/
  kwenza/     kwenza.toml + src (symlink -> ../../../examples/hello-world/src)
  maven/      pom.xml + src (same symlink), with the Maven wrapper (./mvnw) committed
  gradle/     build.gradle.kts + src (same symlink), with the Gradle wrapper (./gradlew) committed
  .cache/     isolated dependency caches (gitignored, regenerated on demand)
----

`src` is a symlink into link:../../examples/hello-world[`examples/hello-world`] for every tool
variant, not a copy — see link:../README.adoc[`benchmarks/README.adoc`] for why. Both wrappers are
committed so anyone cloning this repo can run the Maven/Gradle sides without either tool
pre-installed — same reasoning as `bin/kwenza` needing nothing but a JDK.

== Running it

The actual timed comparison is the shared `benchmarks/Bench.java` harness, run from the
`benchmarks/` directory:

[source,bash]
----
cd ../
java Bench.java hello-world cold       # wipe .cache/, time one real-network-fetch build per tool
java Bench.java hello-world warm 10    # ensure .cache/ is populated, time N clean rebuilds
java Bench.java hello-world both 5     # (default) cold pass, then a warm loop
----

See link:../README.adoc[`benchmarks/README.adoc`] for the full harness usage, including running
every scenario together (`java Bench.java all`). `.cache/` (`kwenza-m2/`, `maven-m2/`,
`gradle-home/`) is fully isolated from your real `~/.m2` and `~/.gradle`, same as before.

== Reading these numbers honestly

This is a one-file project, so it mostly measures **fixed tool overhead** — JVM startup, class
loading, dependency resolution machinery — not compile-at-scale throughput. A real multi-module
project would tell a different story, especially around Gradle's incremental build and
up-to-date checks, which this scenario doesn't exercise at all (there's nothing to incrementally
rebuild in a single file).

Three things this benchmark *has* established, each verified directly rather than assumed:

* **kwenza's cold-fetch speed is real**, not a fluke of a warm OS cache — its concurrent
  POM-then-JAR resolution genuinely outpaces Maven/Gradle's more sequential resolvers by roughly
  12x here.
* **kwenza's own logic is fast and stable** — phase-timing diagnostics (`KWENZA_TIMING=1`) show
  ~400ms total for resolve+compile+package, every run, with no meaningful variance.
* **Gradle's daemon is *why* it wins warm**, not because kwenza is doing anything wrong — kwenza
  launches a fresh JVM per invocation and has to cold-load ~10x more classes than a bare
  `java -version` (`javac` internals, XML parsing, HTTP client), a cost a warm daemon simply
  doesn't pay. See link:../../AGENTS.md[AGENTS.md] for the full investigation and why this is a
  known, deliberate trade-off rather than something to "fix" reflexively.
