= Benchmarks
:toc:
:toclevels: 2

Timed comparisons of kwenza against Maven and Gradle, across a growing set of real scenarios.
Every scenario times the exact same source across every tool; only the manifest format
differs (`kwenza.toml` / `pom.xml` / `build.gradle.kts`), because that's the whole point.

== Running it

One shared harness, `Bench.java`, run from this directory:

[source,bash]
----
java Bench.java                          # every scenario, both cold and warm
java Bench.java hello-world              # one scenario, both cold and warm
java Bench.java junit-word-count cold        # one scenario, cold only
java Bench.java junit-word-count warm 10     # one scenario, warm only, 10 clean rebuilds
java Bench.java all both 7 --write-docs      # everything, and regenerate the performance page's figures
----

`Bench.java` is a single-file Java program (JEP 330 - `java Bench.java ...` compiles and runs it
directly, no build step) rather than a shell script: this repo already has more benchmark logic
than a shell script comfortably holds once there's more than one scenario and more than one
per-tool operation to time, and it's already a Java codebase. It replaces the older
per-scenario `run.sh`.

Four tools are timed, not three: kwenza, Maven, Gradle with its daemon (`./gradlew`) and Gradle
without it (`./gradlew --no-daemon`). kwenza and Maven start a fresh JVM every time, so Gradle's
warm daemon isn't a like-for-like comparison on its own; the no-daemon line is. Both Gradle lines
use the same `gradle/` project directory. See the performance page on kwenza.dev for the reasoning.

`cold` mode wipes each scenario's isolated `.cache/` first and times one real-network-fetch run
per tool; `warm` mode primes the caches (if needed), then times `N` clean rebuilds per tool and
reports min/median; `both` (the default) does cold then warm. `.cache/` (`kwenza-m2/`, `maven-m2/`,
`gradle-home/`) is fully isolated from your real `~/.m2`/`~/.gradle` per scenario, via
`KWENZA_REPO`, Maven's `-Dmaven.repo.local`, and a scoped `GRADLE_USER_HOME` — safe to re-run
anytime. `cold` mode leaves Gradle's downloaded wrapper *distribution* alone (re-fetching a
~120MB tool binary isn't part of what's measured).

`package` always means compile+package only, for every tool — Maven's `package` and Gradle's
`build` both run the test phase first by default, which would silently make "package" include
test execution for those two but not for kwenza. So `package` here is Maven's
`package -Dmaven.test.skip=true` and Gradle's `assemble` (neither depends on `test`), and `test`
is its own separate, explicitly-timed operation wherever a scenario has one.

== Scenarios

[cols="1,2,1"]
|===
|Scenario |What it measures |Operations

|link:hello-world[`hello-world`]
|Fixed per-invocation tool overhead on a trivial one-file app: JVM startup, class loading,
dependency resolution machinery.
|`package`

|link:junit-word-count[`junit-word-count`]
|The same, plus `kwenza test` vs. `mvn test` vs. `gradle test` — a small library with real JUnit 5
and Mockito tests, not a throwaway.
|`package`, `test`

|link:commons-lang3[`commons-lang3`]
|Real compile work: https://github.com/apache/commons-lang[commons-lang3], 259 main source files
and about 100k lines, no dependencies. javac dominates, so this is where kwenza's cold JVM stops
mattering and Gradle's warm daemon (which keeps a JIT-hot compiler) is the thing to beat.
|`package`
|===

`commons-lang3` is the one scenario whose source isn't in this repo: `Bench.java` clones it, pinned
to a commit, into `commons-lang3/.cache/src` on first use, and each variant's `src` is a symlink
into that checkout (dangling until then). The main sources only are built, never the tests
(`package` skips them for every tool).

== Keeping the page current

`--write-docs` (only valid with `all both`) writes everything the performance page takes from a
run, so none of it is typed by hand:

* `docs/modules/ROOT/partials/benchmark-results.adoc`: the environment table (CPU, OS, JDK, Maven and
  Gradle versions, kwenza commit, date), the tables, and the exact command run for every tool and
  operation, generated from the same `command(...)` the harness executes
* `docs/modules/ROOT/images/benchmark-warm.svg` and `benchmark-cold.svg`: the charts

The prose on the page (`docs/modules/ROOT/pages/performance.adoc`) is written by hand and
describes methodology and how to read the results, without quoting numbers. If you change what a
scenario or operation does, or add a tool, update that prose too: the generated commands table
will already be right, the explanation of them won't.

Refreshing is a manual workflow, `.github/workflows/benchmarks.yml` (Actions > Refresh benchmark
figures > Run workflow), which reruns everything and opens a PR with the regenerated files. It's
not triggered by merges: a full run takes a quarter of an hour, shared runners give different
numbers from a laptop (the environment table says which you're looking at), and the figures only
need refreshing when something changes enough to matter, such as a release.

== Regression check: base vs head

`Regress.java` answers a different question from `Bench.java`: not "how does kwenza compare to
Maven", but "did this change make kwenza slower". It takes two kwenza jars and runs both against
a real project, interleaved, then fails if head is meaningfully slower.

[source,bash]
----
java Regress.java <base-jar> <head-jar> [runs] [threshold-percent]
----

The project is the `commons-lang3` scenario above, sharing its checkout. It uses
`commons-lang3/kwenza-deps/` rather than the scenario's own `kwenza/` manifest: that one has no
dev-dependencies, to match the Maven and Gradle variants, whereas the resolve operations below need
a dependency graph to resolve. It's here because the hello-world scenarios are almost all fixed JVM startup, so a change to the
compile path barely moves them; here javac is about 85% of a build.

[cols="1,3"]
|===
|Operation |What it exercises

|`package (no deps)`
|Resolve from the lock, javac over the whole tree, jar. No dependencies to download.

|`resolve (warm cache)`
|Resolve the dev-dependency graph with no lock, POMs and jars already cached: POM parsing and
version mediation, no network.

|`resolve (download)`
|The same from an empty cache, so real downloads and checksum verification. The caches are
isolated, as above. Capped at 5 runs, and the noisiest of the three because it's network-bound.
|===

Why two jars in one run instead of a stored baseline: absolute times on shared CI runners vary
between machines and between days, but two jars measured alternately seconds apart share the
noise. A run fails only when head's median *and* its minimum are both more than the threshold
(default 15%, and at least 50 ms) slower than base's; the median alone flags a busy machine, the
minimum alone a lucky run. Two identical jars compared on a laptop showed a median 13.7% apart
and a minimum 1% apart, which is why both are required.

CI runs it on every pull request (`.github/workflows/perf.yml`), building base from the PR's
target branch, and writes the table to the job summary. Locally, build the two jars however you
like, for example `bin/kwenza package` on each branch and copy the jars aside.

Not covered yet: a project with a much larger dependency graph (Cargo's resolver benchmarks use
captured real-world manifests and locks for this), tests, and trends over time on `main`.

== One copy of the source, not three

Every tool variant's `src/` is a symlink into the corresponding `examples/*` project
(`benchmarks/hello-world/kwenza/src -> ../../../examples/hello-world/src`, and likewise for
`maven`/`gradle` and for `junit-word-count`) — never a copy. This isn't cosmetic: `examples/hello-world`
and its benchmark copy had already silently diverged (different printed message) before this
convention existed, discovered by just diffing them. Symlinking makes that class of drift
structurally impossible instead of something to remember to keep in sync by hand.

Deliberately **not** shared: the manifest (`kwenza.toml`/`pom.xml`/`build.gradle.kts`),
`kwenza.lock`, and build output. Maven and Gradle need their own manifest format anyway, so
there's nothing to share there beyond a couple of dependency coordinates — small, low drift risk,
unlike full source files. And a `cold` run has to delete `kwenza.lock` to force a genuine
re-resolution as part of what it measures; if that lock file were the same file as the example's
(via a directory-level symlink instead of a `src`-only one), every cold benchmark run would delete
and regenerate the example's own committed lockfile as a side effect. Keeping the manifest/lock
local to each benchmark variant avoids that entirely.

Wrapper infrastructure (`mvnw`/`.mvn/`, `gradlew`/`gradle/wrapper/`) is committed per scenario, not
shared or symlinked — that's normal, generic, tool-generated boilerplate every real Maven/Gradle
project commits its own copy of, with no authored content and no drift risk. Each new scenario's
wrapper files are copied from an existing one so the Maven/Gradle *versions* being benchmarked stay
identical across scenarios.

== Adding a scenario

1. Add the real project under `examples/` first, if it doesn't already exist there as a kwenza
   example — `benchmarks/` never originates source, only times it.
2. Create `<scenario>/{kwenza,maven,gradle}/`, each with its own manifest (matching the example's
   dependencies) and a `src` symlink into the example, as above. Copy wrapper files from an
   existing scenario rather than regenerating them.
3. Add a `ScenarioSpec` entry to `Bench.java`'s `SCENARIOS` list with the operations that scenario
   should time.
4. Run `java Bench.java <scenario> cold` once to generate and commit `kwenza.lock` for the kwenza
   variant.
